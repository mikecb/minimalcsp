# Reviewing a minimalcsp policy

`gencsp` builds a policy from what a page was seen to do. Everything in it is there because of something observed, so it doesn't guess. Two questions need a judgment about other companies' services that one page load can't settle, and this skill is for making those calls with the site's owner:

1. Which third-party scripts should be pinned, so that a changed one is blocked?
2. Which allowed hosts could an attacker use to receive stolen data?

Both matter for the same threat: a script the site trusts gets changed at its source. In November 2026, attackers changed the Optimizely snippets of about 178 sites, and the code ran from a URL each site already allowed. The policy can't stop that script arriving. It decides what the script can do next.

## Get the facts first

If you can run commands and `gencsp` is installed, collect two runs. The first is the policy the site should deploy. The second is only for its `change:` lines, which hold each script's hash.

```bash
gencsp -scripts nonce -pages 20 https://example.com
gencsp -scripts hash -no-verify -pages 20 https://example.com
```

Large pages may need `-timeout 2m`, and some containers need `-no-sandbox`. If you can't run it, work from output the person pastes, and say what you're missing: one of the two runs, or a run that covered a single page.

Then find out what each page is for, as the next section describes, because that sets how strict the rest of the review should be.

Read stderr as well as the policy:

- `warning: a nonce trusts the scripts from <host> ...` names each outside host whose scripts could load anything if that host were compromised. These hosts are the list for part 1.
- `warning: couldn't hash <url>` means a script can't be pinned as it's served, usually because its host doesn't send CORS headers.
- `blocked:` lines are inline code the policy will block, which the site has to rewrite: `eval`, event handlers such as `onclick`, and `style` attributes. Mention them, since the policy breaks the page until they're fixed, but they aren't what this review is for. Never suggest `'unsafe-eval'`, `'unsafe-inline'` or `'unsafe-hashes'` to make them go away. `'unsafe-eval'` in particular lets a compromised script run code that the rest of the policy would have stopped.
- `change: every script element in the page as served needs the nonce` is the one page change a `nonce` policy needs: the server adds a new nonce to each script tag on every response.
- `change: <url> needs integrity=...` lines in the `hash` run cover every script, including the site's own, because that mode pins everything. For a site deploying the `nonce` policy, they're a list of hashes to choose from in part 1, not a list of things to do.

## What the page handles

The same third-party script is a small risk on a blog post and a serious one beside a card number field. Before sorting scripts and hosts, work out what each page in the run handles, and whether a rule applies to it that the site has to meet whatever you'd otherwise recommend.

Ask the person. They know which pages take payments or sign people in, and which standards their organization answers to. The page helps too: `gencsp -exact-paths` lists what it loads, and a payment provider's script or frame, a password field, or a form asking about health says a lot. Don't decide that a page is unimportant from its URL.

Sort each page into the strictest group that fits:

- **Card payments.** A page that takes card numbers, or that embeds or redirects to a payment provider's form, falls under PCI DSS. Since 31 March 2025 two of its requirements are about exactly this threat. Requirement 6.4.3 wants every script on a payment page authorized, its integrity assured, and an inventory kept saying why each one is needed. Requirement 11.6.1 wants a way to detect unauthorized changes to the page's scripts and security headers as the browser receives them, checked weekly or as often as the organization's own risk analysis sets.
- **Sign-in and account pages.** Passwords, one-time codes, session cookies and password resets. No single standard covers these everywhere, but a script here can take over accounts, and the organization's own security policy or its auditors usually have something to say.
- **Regulated personal data.** Health details, government IDs, financial records, children's data. Laws such as HIPAA and GDPR care where this data goes, so every third-party host that receives anything from these pages is a disclosure to account for, whether or not an attacker is involved.
- **Pages that lead to those.** A home page with a "Log in" or "Pay" link takes no secrets itself, but a script on it can change where the link goes. Treat it nearly as strictly as the page it leads to.
- **Everything else.**

For the first three groups, the default flips. Elsewhere a third-party script stays unless there's a reason to remove it. Here it goes unless someone can say why the page needs it, and what remains is pinned or served from the site's own origin. "Leave it, and rely on part 2" isn't an acceptable answer on these pages. A separate, tighter policy for them is reasonable: run `gencsp` on those pages alone, with `-scripts hash` if their scripts allow it.

Here is how `gencsp`'s output lines up with the two PCI DSS requirements, so you can say what's covered and what isn't:

| Requirement | What helps | What's still missing |
|---|---|---|
| 6.4.3, authorized | The policy allows only scripts with the nonce or a listed hash | Someone has to approve each script. The tool only records what it saw |
| 6.4.3, integrity | `integrity` attributes, from part 1 or `-scripts hash` | Scripts loaded by other scripts, and any that can't be pinned |
| 6.4.3, inventory | The `change:` lines of a `hash` run list every script in the page | The written reason for each, and scripts added after load |
| 11.6.1, detecting changes | `gencsp verify` on a schedule, and `report-uri` in the enforced policy | Proof it runs as often as required, and someone who acts on an alert |

A policy from `gencsp` supports these requirements. It doesn't make a site compliant, and you shouldn't say it does. Which requirements apply depends on how the site takes payments. A site answers for the scripts on its own page, not for those inside a payment provider's frame, and the rules for sites that only embed a provider's form have changed more than once. Standards also get revised. So name the requirement, say what the policy does toward it, and tell the person to confirm the details against the current standard and with whoever assesses them. If you can look the current text up, do that before quoting a requirement number.

### What the run didn't see

A run records what the page did while Chrome had it open. It doesn't accept a consent banner, open a chat window or log in, so whatever loads after those is missing from the policy and will be blocked. Look for the gaps before judging what's there: a script host with nothing matching in `connect-src`, or a tag manager with no collectors. Tell the person what looks missing, because the hosts that turn up after consent are often the shared collectors part 2 is about. `Actions` in the library, or report-only mode on the live site, will find them.

## Part 1: which scripts to pin

A nonce trusts a script whatever it contains. An `integrity` attribute on the same tag makes the browser refuse the script if its content changes, and this works alongside the nonce, with or without `'strict-dynamic'`. The policy doesn't change. Only the tag does:

```html
<script nonce="{{.Nonce}}" src="https://cdn.example/lib.js"
        integrity="sha256-..." crossorigin="anonymous"></script>
```

The hash comes from the `change:` line for that script in the `hash` run. A cross-origin script needs `crossorigin="anonymous"` and a host that sends CORS headers.

Pinning has a cost: when the vendor changes the script for a good reason, the page loses it without any error the visitor sees. So sort each third-party script into one of these, and say why:

- **Pin it.** The URL names an exact version or a content hash, or it's a library from a CDN. Its content shouldn't ever change, so a change is an attack or a mistake.
- **Pin it after changing the URL.** The URL names a range or the latest version, such as `@^2` or `@latest`. Point it at an exact version first, then pin that.
- **Don't pin it as served.** The vendor changes it as part of the service: tag managers, experimentation and personalization snippets, analytics loaders, chat widgets, consent banners. A pin would break the page on the vendor's next release. Offer the alternatives below instead.
- **Can't pin it.** `gencsp` couldn't hash it. Say so, and treat it as unpinned.

For a script that can't or shouldn't be pinned, the options are, from strongest to weakest:

1. Keep it off the pages that matter most. A vendor script that isn't on the checkout page can't read a card number there. On a payment, sign-in or regulated-data page, this is the answer unless the page can't work without the script.
2. Serve a reviewed copy from the site's own origin, updated when the site deploys. This gives up the vendor's instant updates, which for some services is the point of the product, so check before suggesting it.
3. Leave it, and rely on part 2 to limit where data can go.

Look for evidence before you sort. The shape of the URL usually says most. After that, a short `Cache-Control` lifetime or a recent `Last-Modified` points to a script that changes, and the vendor's documentation often says whether it supports Subresource Integrity. If you fetch a script to compare its hash, hash the decoded body, not the compressed bytes. When you can't tell, say that, and say how the person can find out. A wrong guess either breaks their site or leaves them exposed.

Only scripts in the page as served can be pinned this way. What those scripts load in turn has no tag to put a hash on, so a tag manager's own loads stay unpinned whatever you do with its first file.

A host the site itself runs, such as its own CDN on another domain, gets the same warning from `gencsp`, because nothing in a page says who owns a host. Ask if you're not sure. Scripts the site's own team deploys don't need pinning on these grounds.

## Part 2: which hosts can receive data

A compromised script can send what it steals to any host the policy allows. `gencsp` lists only hosts the page really uses, which keeps out a domain the attacker registered. It can't know which of those hosts would also deliver data to an attacker.

Check every host outside the site's own origin in `connect-src`, `img-src`, `form-action`, `frame-src` and `media-src`. Any request can carry data in its URL, so an image host counts as much as an API. Sort each host:

- **The site's own**, or a vendor host that only serves this customer, such as a subdomain named for their account.
- **A shared collector.** Anyone with an account receives data sent to the same host, told apart only by an ID in the request. Analytics and error-tracking collectors, form backends, file and object storage, and webhook receivers are the common cases. An attacker opens their own account, and the policy allows the request because the host matches. Flag these.
- **A shared host that serves files.** A vendor's CDN that every customer loads from. Nothing about it suggests another customer can read what's sent there, but you're judging from the outside, so say that.
- **Too wide to judge.** A wildcard, or a whole scheme such as `https:`. `gencsp` doesn't emit these, so someone added it by hand. `data:` in `img-src` is fine, since nothing leaves the browser.

`frame-src` needs a different question. A framed page isn't bound by this policy, so it can send data anywhere. Ask whether anyone else could get their own page served from that host, not whether the host collects data.

One host can need both judgments: its scripts in part 1, and what it receives here.

For a flagged host, suggest in this order:

1. Remove it if the page doesn't need it. Ask what it's for when it isn't obvious.
2. Send the requests through the site's own origin, so the policy allows only `'self'` and the site's server decides which account receives them. Many analytics products document a first-party proxy.
3. Keep the service off the pages that matter most.

`-exact-paths` lists full URLs instead of hosts. It's tighter, but it rarely helps here: the account ID usually sits in the query or the body, which a policy can't see, and browsers stop checking the path after a redirect.

Don't call a host safe. You're judging from its name and what you know of the service, and services change. "I found nothing that lets another account receive data here" is as far as the evidence goes.

## What to tell them

Keep it short enough to act on. Lead with what to change. Give each thing that needs action its own line, and cover everything you judged fine in one line per section. If nothing can be pinned as served, say that first instead of leaving the section empty.

```markdown
## What these pages handle
- <page or group of pages>: <what it handles>. <any standard that applies, and what it asks for>

## Pin these scripts
- <url>: add integrity="sha256-..." crossorigin="anonymous". <why it won't change>

## Leave these unpinned
- <url>: <why>. <which alternative you recommend>

## Hosts that could receive stolen data
- <host> in <directive>: <what it is>. <what to do>

## What the run didn't cover

## What this policy still can't stop
```

In the last section, be plain about the limits, because people over-trust a policy that passes a scanner. A script that still runs can change what the page shows, such as a payment address, without sending anything. It can send the visitor to another site with data in the URL. And the policy only covers pages that send it.

After they make changes, have them check the result, since a wrong hash or a missing CORS header fails only in a browser:

```bash
gencsp verify -pages 20 https://example.com
```

## Staying inside the tool's rules

The policy text comes from `gencsp`, so suggest changes to the page and to what it loads, then a new run. Don't hand-edit the policy to add hosts to `script-src`, `'unsafe-inline'`, `'unsafe-eval'` or `'unsafe-hashes'`. Each of those removes a protection that the rest of this review assumes is there. If the site can't work without one of them, that's the finding to report.
